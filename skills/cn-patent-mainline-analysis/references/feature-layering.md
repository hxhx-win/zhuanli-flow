# 项目保护路径候选

本文件说明如何基于已确认技术方向和核心资料生成保护路径候选。它不保存某个固定项目的候选，也不要求生成或回写扫描区。

## 候选生成输入

生成候选前，至少掌握：

- 项目根目录和主要入口。
- 核心算法、控制链路或数据处理流程。
- 实验、仿真、图表或质量分析证据。
- 参考专利样稿或现有草稿。
- 用户期望保护的对象和业务/工程目标。

## 保护路径输出格式

在已确认技术方向下，每条保护路径候选建议包含：

- 保护路径名称。
- 保护客体：方法、装置、系统、介质或组合。
- 技术问题。
- 核心技术手段。
- 预期技术效果。
- 关键证据来源。
- 创造性风险和待确认事项。

## 技术特征分层输出格式

`mainline-analysis.md` 的 `## 技术特征分层` 不应只列“必要/优选/实施细节”三个层级，还应为下游起草提供可消费的作用和落位信息。建议使用表格或等价结构，每一项至少包含：

| 字段 | 含义 |
| --- | --- |
| 特征编号 | 如 F1、F2、O1、D1，便于权利要求、实施方式和审稿引用 |
| 层级 | 必要、优选、实施细节 |
| 技术特征 | 平台无关的技术描述，不使用文件名、函数名或脚本名替代 |
| 技术作用 | 该特征在方案链路中承担的作用 |
| 技术效果 | 该作用带来的可说明或可验证效果 |
| 主体归属 | 方法步骤、第一设备、第二设备、装置模块、系统交互、介质指令、结构部件等 |
| 适合写入位置 | 独权候选、从权候选、实施例支撑、替代实施方式、分案保留、暂不写入 |
| 证据来源 | 代码、技术交底、实验数据、设计文档或用户授权假设 |
| 待确认事项 | 缺少参数、效果证据或实施细节时明确标注 |

必要技术特征应能形成独立权利要求的最小技术闭环；优选技术特征优先用于从属权利要求；实施细节优先用于具体实施方式、替代实施方式或附图支撑。若某项特征没有明确技术作用或技术效果，不应直接进入独立权利要求。

## 保护客体和主体拆分建议

当技术方案涉及多个执行主体或结构部件时，主线分析阶段应给出保护客体拆分建议：

- 多主体方法：标注第一主体、第二主体、云端、终端、发送端、接收端等主体归属，并说明是否需要分别起草主体侧方法。
- 装置/系统：标注模块、单元或部件之间的连接、通信、调用或装配关系。
- 结构类方案：标注部件集合、空间关系、连接关系、投影关系、运动关系和关键约束。
- 介质/设备：标注哪些方法步骤适合由处理器执行，哪些模块适合落入设备权利要求。

保护客体判型结果应传递给正式起草阶段，用于决定读取哪个分类 reference：方法类和多主体方法读取 `method-claim-drafting.md`，结构类读取 `structural-claim-drafting.md`，混合类读取所有命中的细分 reference。

## 人工收敛建议

- 优先选择证据最强、区别特征最清楚、技术效果最稳定的一条保护路径作为独立权利要求方向。
- 不把文件名、函数名或脚本名直接写成技术特征，除非它本身就是发明点。
- 其余保护路径可用于从属权利要求、替代实施方式或后续分案。
- 若保护路径之间差异只体现在参数或场景，优先合并为一条路径并在从属权利要求中分层。
- 对每个候选发明点都要判断“适合写入位置”；不要把可选实施、异常回退、缓存策略、平台适配或整机应用直接上提为独权核心，除非其本身是检索后确认的区别特征。

## 统一表头（供下游 disclosure-draft 抽取迁移）

技术特征分层表头：

| 特征编号 | 层级 | 技术特征 | 技术作用 | 技术效果 | 主体归属 | 适合写入位置 | 证据来源 | 待确认事项 |
|---|---|---|---|---|---|---|---|---|

字段约定：

- **特征编号**：F-1、F-2、… 全局唯一
- **层级**：`必要 / 优选 / 实施细节` 之一
- **待确认事项**：单行描述；为空时写"无"，便于下游抽取
- **证据来源**：指向 `evidence-matrix.md` 中 TP-* 或 G-* 编号
