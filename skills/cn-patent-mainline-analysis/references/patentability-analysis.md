# 检索输入整理与保护路径设计

## 必做的检索输入整理

主线分析阶段不做外部现有技术检索，不判断新颖性或创造性，也不写权利要求。进入检索前，必须把以下问题整理清楚：

1. 已确认技术方向是什么
2. 项目资料中有哪些可由证据支撑的技术特征
3. 这些技术特征预期解决什么技术问题、产生什么技术效果
4. 哪些保护路径候选和候选发明点需要外部检索验证

若无法完成检索输入整理，则必须输出：

- 当前能确定的项目内技术特征
- 尚缺失的项目证据或用户确认事项
- 暂不宜送检索或写入候选发明点的内容

若用户要求判断“哪个保护路径真正更有创造性”“最接近现有技术是什么”“哪些发明点真正可主张”，必须进入 `cn-patent-prior-art-search` skill。`claimable_invention_points`、`closest_prior_art` 和 `distinguishing_features` 只能由检索阶段产生。

## 保护客体判断规则

优先判断更适合保护为哪一类：

- 方法
- 装置
- 系统
- 设备
- 存储介质
- 方法加装置或设备的双保护

判断规则如下：

- 核心创新在算法流程、路径规划、约束求解、轨迹生成时，优先写"方法"
- 核心创新在模块划分、硬件连接、控制架构、平台构型时，优先写"装置、设备或系统"
- 若项目既有算法又有平台执行闭环，可考虑"方法独立权利要求 + 装置或设备独立权利要求"

## 必须给出保护路径候选

当已确认技术方向下存在多种保护写法时，不要直接替用户拍板，必须列出：

- 保护路径名称
- 保护重点
- 证据强弱
- 风险点
- 检索输入摘要

## 技术特征分层

技术特征必须分成三层：

### 必要技术特征

没有这些特征，该发明就不成立，优先进入独立权利要求。

### 优选技术特征

用于细化保护范围、增强稳定性或提高技术效果，优先进入从属权利要求。

### 实施细节

用于支撑说明书和实施方式，但通常不宜写入独立权利要求，例如：

- 具体软件环境
- 调参过程
- 图像显示界面
- 脚本调用
- 实验参数
- 硬编码阈值

输出时应给出分层表：

| 技术特征 | 层级 | 作用 | 支撑证据 | 是否适合写入独立权利要求 |
|---|---|---|---|---|

## 候选发明点用途表

在进入外部检索前，先建立候选发明点用途表。每个候选发明点至少记录：

- 发明点名称
- 解决的技术问题
- 所属保护路径
- 关键技术步骤或模块
- 对应证据文件
- 预期技术效果
- 写入独立权利要求的风险
- 写成从属权利要求的可行性
- 用途：`独权核心`、`从权候选`、`实施例支撑`、`替代实施方式`、`分案保留` 或 `暂不写入`
- 是否需要用户确认

后续使用规则：

- 本阶段只标注“可能用途”，不得把候选发明点直接升级为独权核心。
- 经检索确认后的可主张发明点写入 `claimable_invention_points`。
- Gate A 用户确认 `selected_mainline` 后，正式稿才可据此设计独立权利要求。
- 不要把多个证据不足或未经检索确认的点强行拼成一个宽泛保护路径。

## 默认工作方式

收到任务后，默认按以下顺序推进：

1. 明确用户要的是哪类交付物
2. 确认 `selected_direction`，不得脱离已确认方向重新推荐新方向
3. 抽取技术问题、证据支撑的技术特征和候选保护客体
4. 建立技术特征分层表和候选发明点用途表
5. 列出保护路径候选、检索输入摘要和待检索确认问题
6. 最后给出证据来源、风险点、待确认事项和补强方向
