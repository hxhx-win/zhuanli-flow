# 交底书起草纪律

> 本文件由交底书生成 subagent 在 disclosure-generation 阶段读取。评审 subagent 不必读。

技术交底书 disclosure-draft.md 面向三类读者：代理师起草、发明人复核、专利部门一眼看核心。subagent 起草必须遵守：

## 1. 编号语言

正文禁止内部编号(IP-N、C-IP-N、DF-N、F-N、Ref-N、R-N、BQ-N、G-N、PN、TP-N、M-N、Q-N、D-N 等带连字符或数字后缀的字母编号一律不得出现)。

替换为:

| 内部编号 | 正文写法 |
|---|---|
| IP-N / C-IP-N | 发明点一 / 发明点二 ……(独权候选用"发明点",从权候选用"附加技术特征") |
| DF-N | 区别特征一 / 区别特征二 …… |
| Ref-N | [文献 1] / [文献 2] ……(中文专利惯例) |
| 缺陷/技术问题/有益效果 | （1）（2）（3）……（使用全角括号，与交底书模板第 4 节保持一致） |

合并语义(如"IP-1 与 IP-5 合并为 C-IP-1")只写最终形态"发明点一",不写合并过程。

## 2. 编排术语黑名单

正文禁止: Gate A、step 1/2/3/4、state.*、verdict、go/revise-*/stop-*、risk_acknowledged、subagent、AskUserQuestion、orchestrator、handoff、MQL、decision_readiness、chain_check、oneliner、use_as、"待起草前决策"等。

未确认字段写"(待用户确认)"留白,不写"待 Gate A 段决策"或"由编排器写入 state"。

## 3. 代码层细节剥离与术语白名单

### 3.1 三类术语处理（铁律：判断顺序自上而下）

**A 类 — 行业通用词，原样保留（鼓励使用）**：

> 任何中文专利数据库 / Google Patents / arXiv 能搜到的标准词。这是读者认知的锚点，也是检索可见性的来源，不要换名字。

参考白名单（按需扩展，但只往这一类里加，不要进 B/C）：

- 传感与运动：IMU、惯性测量单元、惯性传感器、陀螺仪、加速度计、四元数、欧拉角
- 计算机视觉与防抖：电子防抖、EIS、光学防抖、OIS、视频防抖、视点稳定、滑动滤波、平滑滤波、CORI/IORI 元数据
- 框架/运行时：GStreamer、流水线、管线、流式管线、自定义事件、下游事件、事件总线、元数据轨道
- 并发与资源管理：互斥量、互斥锁、读写锁、引用计数、生命周期、原子计数、信号量、内存屏障
- 数据结构与算法：哈希表、键值对、批次、分段、段索引、文件索引、缓存
- 视频与媒体：视频帧、像素帧、帧元数据、容器格式、mp4、SDK、API

> 上述清单为**示范白名单**，subagent 起草前应该结合上游 evidence-matrix 与 mainline-analysis 的术语条目，按 A/B/C 分类。原则不是"凑足白名单"，而是**"能用通用词就不要造新词"**。

**B 类 — 项目代码符号，必须抽象为 A 类组合（用通用词描述）**：

正文禁止：
- 代码路径与行号（如 flowstate_shared_core.h:62-80）
- 类型名 / 类名 / 实例名 / 函数名（如 FlowstateSharedCore、gst_flowstate_bino_init、PLUGIN_NAME）
- 代码符号 / 字段名 / 常量名（如 ref_count、guard、core_tag、multifile-imu-preload、GST_EVENT_CUSTOM_DOWNSTREAM）
- 具体宏 / 头文件 / 库 API 名

抽象示范：
- ❌ "FlowstateSharedCore 通过 ref_count 管理生命周期"
- ✅ "进程内的视频防抖核心对象通过引用计数管理生命周期"（"视频防抖核心"由"视频防抖"+"核心对象"两个 A 类组合而成；"引用计数"是 A 类直用）

**C 类 — 自造中性词，禁止（重要！）**：

不允许 subagent 为了避开 B 类代码符号，自造一层"中性中文术语"。如果一个词在中文专利文献 / 行业教材里搜不到，就不是术语，是 subagent 的代号。常见自造迹象（错误示范）：

| 自造词 | 错在哪 | 正确写法 |
|---|---|---|
| 防抖子流水线 | "子流水线"非通用词 | "防抖处理流水线" / "视频防抖流水线" |
| 视频防抖算法核心 | "算法核心"非术语 | "视频防抖核心模块" / "视频防抖处理单元" |
| 共享状态对象 | "共享状态对象"自造 | "共享资源容器" / "共享上下文" |
| 子流水线类型标签 | 无对应通用词 | "流水线类别标识" / "处理流水线分类标签" |
| 段索引 | "段索引"非通用词 | "分段编号" / "视频分段索引" |
| 批次管理器 | "批次管理器"自造 | "数据批次缓存" / "分段数据缓存" |
| 视点控制配置一致性 | 长名词链 | 拆为正文动词句式：分散写到第 4 节实现段，不进术语表 |

### 3.2 第 1 节"缩略语和关键术语定义"的取材规则

第 1 节只收以下三类术语，三类之外一律不进：

1. **英文缩略语**：英文缩写 + 中文全称 + 一句中文解释（IMU、EIS、OIS、API、SDK 等）
2. **本发明赋予具体所指的领域常识词**：词本身在公开渠道可检索（无人机、飞行视角切换、360 全景视野、无人机眼镜、无人机遥控器、引用计数、互斥量等），但本发明对它的所指做了收窄或具体化，需在术语表里明确"本发明所讨论的 X 指 ……"，给正文锚一个交流基线
3. **本发明对部件 / 动作的中文命名**：名字必须由通用词组合而成（"飞行视角"+"切换"、"视频防抖"+"核心模块"），且后面正文反复出现需消歧；命名一旦在术语表登记，正文统一只用这一种写法

**绝对禁止**：

- 把代码符号（FlowstateSharedCore、ref_count）翻译为中文术语充数
- 把项目内部自造、行业不流通的中性词（"防抖子流水线""共享状态对象"等 § 3.1 C 类）伪装成"关键术语"
- 收录正文从不引用的词
- 同一对象起两个不同名字（如"防抖核心""防抖算法核心"），术语表里登记的名字与正文写法必须一致

如需解释项目中某个具体机制，写到第 4 节"本发明的实现"段中作为动词陈述，不要列入术语词典。代码层证据由代理师在起草正式稿"具体实施方式"时从 evidence-matrix.md 与 pre-draft-review.md 直读补入，不在交底书出现。

## 4. 语言节奏

### 4.1 三条硬规则（不可违反）

1. **单句中文 ≤ 55 字**（以"。"或"；"为终止符；超过必须断句重写）
2. **同一句中禁止出现 if/else 分支**：含"若……则……；若……则……"或"如果……那么……否则……"句式必须**拆为多句或序号化列表**
3. **同一段落中同一术语重复出现 > 3 次** → 改写为序号化列表（每个分支一行）

### 4.2 反例与正确写法

**反例 A — 单句塞 if/else 分支**：

> ❌ "在状态保护互斥量保护下读取引用计数，若引用计数为零则分配视频防抖核心并对其内部互斥量执行初始化，使引用计数加一并返回；若引用计数大于零则直接复用既有视频防抖核心，使引用计数加一并返回。"（97 字，分号嵌套两个分支，"引用计数"出现 5 次）

> ✅ 正确写法（拆为序号列表）：
>
> 在状态保护互斥量保护下读取引用计数。后续动作按引用计数当前值分两种情况：
>
> （a）引用计数为零：分配新的视频防抖核心，对其内部互斥量执行初始化，使引用计数加一，返回新核心指针。
>
> （b）引用计数大于零：直接复用既有视频防抖核心，使引用计数加一，返回该核心指针。

**反例 B — 长名词链堆叠**：

> ❌ "本发明在引用计数容器之外引入按子流水线类型字符串路由到独立共享状态对象的分组机制使同一对获取/释放接口在不同标签下分别路由到独立的共享状态对象。"（71 字一句，"独立的共享状态对象"重复出现）

> ✅ 正确写法（拆为两句 + 共享对象只命名一次）：
>
> 本发明引入按流水线类型字符串路由的分组机制。同一对获取/释放接口在不同类型标签下，被分别路由到独立的状态容器。

### 4.3 其他要求

- 段落长度由内容决定，不凑句数
- "其一……其二……其三"类多想法塞一句的写法必须拆成多句或序号化列表
- 优先用句号断句，不优先用分号嵌套
- 一段中超过两次出现并列项时，把并列项改为列表（- 项 1 / - 项 2）

## 5. 语言风格(6 条)

1. 第三人称客观陈述("本发明……"、"该方案……"),不用第一人称("我们"、"咱们")或口语
2. 中文为主,英文术语首次出现时附中文释义;避免中英混杂的句子
3. 不用营销/夸大词:显著、大幅、完美、彻底、革命性、首创、突破性、卓越、领先、开创性
4. 不用模糊词:可能、也许、大概、似乎、应当、理论上、有望、相对而言;陈述事实用"是/否",陈述推论用"由此/因此"
5. 不用解释主观感受、研发故事、商业目的;只描述技术做法、结构、条件、动作、结果
6. 不用比喻、拟人、修辞;技术对象直陈

## 6. oneliner 位置

≤ 60 字中文一句的 oneliner 必须出现在交底书第一行(标题下方)作为引用块 `> ...`。同时仍写入 state 给 handoff-package 消费。oneliner 写不出 (interview_failed) 时引用块留空,不编造。

## 7. 五节逻辑闭环自检（非显式交叉引用）

第 2 节（现有技术方案及缺陷）、第 3 节（技术问题）、第 4 节（完整技术方案）、第 5 节（有益效果）四节内容必须**逻辑上**形成闭环；但**正文不写显式交叉引用**——读者读下来自然顺通即可，不要满纸"对应缺陷（N）→ 技术问题（N）"这种编号互指。

**正文写法（读者可见）**：

- 第 3 节技术问题：自然陈述要解决的问题，不前缀"对应缺陷（N）"。问题来源允许有三类：缺陷反推 / 改进现有功能 / 实现新目的
- 第 4 节按**技术方案自身的系统结构**展开（系统模块 / 处理流程阶段 / 数据流时序），不按"发明点一 / 发明点二"切分小节。"发明点"是评审分析层概念（用于划分独权候选 / 从权候选），不在第 4 节小节标题中出现。每节按"输入/处理步骤/输出/各部件协同"客观陈述
- 从权候选发明点不另起小节，附在对应系统模块/流程阶段的小节末尾作为"附加技术特征"小段
- 第 5 节有益效果：自然陈述"针对……（问题描述），本发明……，由此 ……"；不写"针对技术问题（N），本发明通过第 4 节发明点（N）……"
- 第 4 节末尾"五栏因果链对照表"保留作为代理师起草正式稿和审查员快速核对的内部参照——把"发明点 ↔ 第 4 节段落"的映射收在这张表里，正文不出现"发明点一/二"标题

**起草前隐式自检（subagent 必须回答；不写进正文）**：

1. 第 4 节每个独权/从权候选发明点，是否能映射到第 4 节某个段落落实其实现？
2. 第 4 节每个段落所支撑的发明点，是否能在第 3 节找到对应技术问题？
3. 第 3 节每条技术问题，是否能在第 2 节找到来源（缺陷反推 / 改进现有功能 / 实现新目的）？若是改进型或目的型，第 2.1 节是否描述了"现有方案做什么 / 不做什么"作为差异链锚点？
4. 第 5 节每条有益效果，是否能追溯到"第 4 节相对第 2 节增加/改进了某个具体模块/步骤/流程"？
5. 第 2 节是否包含足以支撑第 5 节差异链的"现有方案"描述？

任一回答否 → 调整内容直至自洽。自检通过后落盘正文，**自检过程不写入交底书**。

## 8. 风险信息只在评审报告

风险登记 / 补证清单 / 待澄清问题 / 缺口数据等不进交底书正文。formal-drafting 起草正式稿时直读 pre-draft-review.md 对应章节。

## 9. 不再生成附录

technical-decision-package.md 不再生成。subagent 只产出 disclosure-draft.md 一份文件。

## 10. 技术方案表达深度（鼓励项）

第 4 节"完整技术方案"在以下三种深度表达适用时，应当使用；不强凑、按方案性质取舍：

1. **LaTeX 数学公式**：算法可被数学化（时间戳计算、滤波公式、坐标变换、信号匹配条件、采样判定等）时，用 `$$...$$` 或行内 `$...$` 表达精确关系，替代纯文字"先算……再算……"。每条公式后用一句中文说明各符号含义与默认取值。
2. **ASCII 状态机 / 流程 / 时序图**：涉及状态切换、阶段流转、事件触发、模块协同时，画 ASCII 图作为视觉锚点（用 `┌─┐ │ ↓ →` 等字符）。图旁配 1–2 句中文说明，不重复图中内容。
3. **关键工程数值表**：把方案涉及的所有默认参数集中登记为一张表，列为"参数 / 默认值 / 说明"，放在第 4 节末尾（template 已含该小节模板）。代理师起草正式稿"具体实施方式"时可直接抄入。

无算法可数学化时不强凑公式；无状态机/事件流时不画图；无可登记参数时不写参数表。
