# 正式稿起草常见错误清单

本文件从 `SKILL.md` 外移而来。起草 subagent 在落盘正式稿前可按本清单做最后一道自检；审稿 subagent 在 direction-05（形式与证据审查）时可作为对照清单。

## 常见错误

- 把分析起草版直接交付（含证据来源章节）→ 必须转为正式稿版，删除 `# 证据来源` 与 `# 风险点与待确认事项`。
- `figure-manifest.json` 输出为 JSON 数组 → 导出脚本静默丢失所有附图；必须顶层为 `{"entries": [...]}` 对象。
- 公式残留伪源 `sum(...)`、`sqrt(...)`、`mu(...)` → 导出失败；公式源按 `references/formula-and-math.md` 规范化。
- 实施方式覆盖计划或证据备注残留在正式稿正文 → 必须移入 evidence notes。
- 为了补足实施方式密度而臆造参数、结构或效果 → 必须改为"待用户确认"事项或阻断起草，回到证据收集流程。
- 把代码标识符（函数名 / 变量名 / 类名 / 枚举常量名）替代技术特征描述 → 必须抽象为技术对象 / 数据结构 / 判定条件 / 执行路径 / 模块关系，代码标识符仅在首次出现时括号辅助。
- 正式稿 Markdown 中使用 `###` 标小标题给"步骤编号 / 参数说明 / 公式推导 / 实验条件 / 风险说明" → 这些应作为正文段落，`###` 仅用于"实施例 N / 可选实施方式 / 替代实施方式"等大节切分。

### 结构类专项

- 把结构类独权写成"步骤 S1、S2"的方法流程 → 结构类不应使用方法流程模板；按部件 + 关系 + 约束组织独权（详见 `structural-claim-drafting.md`）。
- 结构主导方案被误判为方法类，只保护控制流程而遗漏核心部件关系 → 创造性主要来自部件组合 / 连接 / 投影 / 运动 / 材料配合时，按结构类主导处理；判型见 `claim-type-classification.md`。
- 从权只写效果，不写产生效果的结构限定 → 从权附加技术特征必须落到具体部件 / 关系 / 尺寸 / 替代结构，不能只列效果描述。
